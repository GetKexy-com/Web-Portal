# Kexy Custom Rich Editor

A self-contained Angular rich **email** editor component (`<kexy-custom-rich-editor>`). It produces email-safe HTML, supports merge tags with fallbacks, inline image/video blocks, and a design / preview / HTML source view.

> This file is the source of truth for how the editor is built and why. Read it before changing anything in this folder.

---

## How to use it

```ts
import { KexyCustomRichEditorComponent } from './kexy-custom-rich-editor/kexy-custom-rich-editor.component';

@Component({
  standalone: true,
  imports: [KexyCustomRichEditorComponent],
  template: `<kexy-custom-rich-editor [content]="emailHtml"></kexy-custom-rich-editor>`,
})
export class HostComponent {
  emailHtml = '<p>Hi [receiver_first_name],</p>';
}
```

Push content / read it back at runtime via a `@ViewChild`:

```ts
@ViewChild(KexyCustomRichEditorComponent) editor!: KexyCustomRichEditorComponent;

this.editor.loadContent('<p>Hi [receiver_first_name],</p>'); // replace content
const html = this.editor.getHtml();                           // export-ready HTML
```

### Public API (`KexyCustomRichEditorComponent`)
- `@Input() content?: string` — initial email HTML. If omitted, a built-in sample loads.
- `@Input() plainText?: boolean` — when true, `getHtml()`/preview emit the body in a bare document (doctype/head/body) with **NO** email-table shell (for "Plain Text" style emails). Reactive: toggling it re-renders the preview + HTML output (it forwards to `EditorCanvasComponent.plainText` + `refreshOutputs`). Body element styling (inlineEmailStyles) is still applied — only the shell is skipped.
- `@Input() fillHeight?: boolean` — opt-in to **fill-height mode** (default `false`): the editor stretches to fill the bounded height its host gives it and the active view (Design canvas / Source / HTML / Preview) scrolls **internally**, instead of the default content-height model (editor grows with the email, outer container scrolls). Bound to the `fill-height` host class via `@HostBinding`. The host MUST place the editor in a bounded flex context (a flex column with a definite height) or it has nothing to fill — see the send-email offcanvas (`send-email-details-content`). See "Layout / styling".
- `loadContent(html: string)` — replace the editor content (renders chips, hydrates media blocks).
- `getHtml(): string` — current export-ready, inlined email HTML: a **full standalone `<!DOCTYPE html>` document** whose `<title>` is the subject. Note this is never literally empty even when the editor is visually blank — a host that needs an emptiness check must strip tags/media itself (see `brand-conversation-sent`'s `isEmailHtmlEmpty`).
- `getBodyHtml(): string` — the inlined, email-safe **body fragment only** (no document shell, no `<title>`). Use this when embedding the content into an existing page/message rendered via `[innerHTML]` (e.g. a conversation reply): a full getHtml() document would leak its `<title>`/head text as stray content. Backed by `EditorCanvasComponent.getInlinedBodyHtml()`, which `generateEmailHtml` also wraps for getHtml().
- `loadSample()`, `copyHtml()`, `downloadHtml()`, `switchMode('design'|'preview'|'html')`.

## Requirements / dependencies

- **Angular ≥ 17.3** — uses signals, the `output()` function, and `@if`/`@for` control flow.
- Only `@angular/core` and `@angular/forms`. No third-party libraries, no NgModule, no `provideAnimations`.
- **Self-contained**: design tokens, base font, and resets are defined in the component stylesheet **scoped to the `kexy-custom-rich-editor` host** (see `kexy-custom-rich-editor.component.css`). Copying this folder + importing the component is enough — **no external CSS required**.
- The host element is **content-height** (`height: auto; min-height: 360px`) by default: the editor grows with the email it holds and the **outer container scrolls** when content is long — the Design canvas does NOT scroll internally. Don't give the host a fixed/bounded height in this mode (that reintroduces internal scroll). (Preview iframe + Source/HTML textareas are the exception — they can't be content-height, so they get a fixed `min-height`/`height` and scroll internally.) **`[fillHeight]` flips this**: the editor fills the bounded height its host gives it and the canvas scrolls internally instead — used by the send-email offcanvas so the editor uses all available vertical space.

NOTE: the `editor-test-host.component.ts` / `app.component.ts` in the parent project are just a demo harness — NOT part of this package. Don't copy them.

## Architecture

All standalone components. The main component composes the others.

```
kexy-custom-rich-editor.component.ts   Public component. Host element, ViewEncapsulation.None,
                                       styleUrl. Owns @Input content + public API.
kexy-custom-rich-editor.component.css  ALL editor styles + scoped design tokens/resets.
components/
  editor-toolbar.component.ts          Toolbar UI (selector app-editor-toolbar). Calls into the canvas.
  editor-canvas.component.ts           The contenteditable canvas + preview iframe + HTML source
                                       textarea (selector app-editor-canvas). Core editing logic.
  media-inspector.component.ts         Panel to edit a selected image/video block (app-media-inspector).
  fallback-popover.component.ts        Popover to set a merge-tag fallback (app-fallback-popover).
                                       Has its OWN inline scoped styles (hardcoded colors).
services/
  editor-state.service.ts              Signals: mode, sourceMode, selectedBlock, status, htmlOutput,
                                       subject, inspectorTick. providedIn:'root' (see caveat below).
  editor-utils.service.ts              SVG placeholders, file→dataURL, HTML/attr escaping, font-tag
                                       normalization, inline-styling + media-block transform for export.
  merge-tag.service.ts                 Merge-tag registry, chip creation/decoration, [tag] <-> chip render.
models/
  editor.models.ts                     EditorMode, InsertImageOptions, InsertVideoOptions.
```

Wiring: the host component (`ngAfterViewInit`) injects the `EditorCanvasComponent` reference into the toolbar and inspector (`toolbar.canvas = editorCanvas`, etc.).

## Key concepts & decisions

### Merge tags
- Canonical keys (must match the approved build + the backend's send-time resolver): `receiver_first_name`, `receiver_last_name`, `receiver_company_name`, `receiver_phone_number`, `receiver_email_address`, `receiver_website`, `unsubscribe_link`. (The `receiver_*` set was briefly wrong — `receiver_phone`/`receiver_email`/`website` — a post-integration regression; fixed back to canonical.) `unsubscribe_link` (label "Unsubscribe Link") is a **link-type** tag the backend resolves to the recipient's unsubscribe URL; it's separate from the send-email flow's `isAddUnsubscribeLink` checkbox (which auto-appends a link) — the tag lets the user place the link inline. All tags come from the `MergeTagService` registry, so the toolbar `#` picker lists them automatically.
- Syntax in HTML: `[snake_case_key]` with optional fallback `[key fallback=some value]` (canonical **space** syntax). Legacy **pipe** syntax `[key|fallback=…]` is *parsed* for back-compat (`TAG_REGEX` group 3) but **never emitted** — `buildRawTag` always writes the space form.
- In the design canvas they render as **blue pill chips** (label, e.g. "First Name"); on export they're stripped back to raw `[key]` / `[key fallback=…]`.
- **Fallback is stored PER CHIP** on `chip.dataset.mergeFallback` (NOT per-key) so two chips of the same tag can carry different fallbacks — matches the approved build. The `MergeTagService` registry holds `key` + `label` (+ optional `noFallback`). Relevant methods: `getAll`, `getTag`, `labelFor`, `allowsFallback(key)`, `createChip(key, fallback?)`, `decorateChip` (reads the chip's own dataset), `renderChipsInElement`, `stripChipsToRaw` (reads the chip's own dataset), `TAG_REGEX`, `buildRawTag`. The fallback popover writes straight to `currentChip.dataset.mergeFallback`.
- Fallback defaults are empty — `fallback=` is only emitted when a fallback is actually set.
- Clicking a chip opens the **fallback popover**; it shows an **undo (↺) icon** once you change the value (reverts to the value it opened with). When a fallback is set, the chip shows a small **↩ marker** (and `has-fallback` class) — color stays blue. **Link-type tags take no fallback** (`noFallback: true`, e.g. `unsubscribe_link`): both click handlers (`onCanvasClick`, `onSubjectClick`) gate the popover on `mergeTags.allowsFallback(key)`, so clicking such a chip doesn't open the popover. **`onCanvasClick` still explicitly `selectNode`s the clicked chip (all chips, fallback or not) and saves that range** — so a follow-up toolbar action (notably alignment) has a deterministic target. Without this, clicking a `contenteditable="false"` chip (especially one sitting bare in the root, like an inserted unsubscribe link) left an ambiguous/empty selection and the aligner couldn't find its line.
- The toolbar **`#` picker** (in the overflow menu) has a search box and inserts a chip at the caret.
- Chips are rendered on content load and when leaving Source view — NOT live while typing (would disrupt the caret). Typed `[tags]` become chips after a sample/source round-trip.

### Toolbar (`editor-toolbar.component.ts`)
- Flat **inline-SVG icons**, grouped with `.tool-divider` separators. `.toolbar-scroll` is **`flex-wrap: nowrap; overflow: visible`** — the toolbar is **always a single row** at every width; it never wraps and never squishes. (`overflow` MUST stay `visible` — the `⋮` dropdown is absolutely positioned inside the strip and would be clipped otherwise; horizontal spill is contained by `recomputeOverflow` keeping clusters fitting, plus the ancestor `.editor-modal > section { overflow:hidden }`.)
- **Priority-plus overflow.** The main strip is built from collapsible **clusters** (`GROUPS` in `editor-toolbar.component.ts`), each rendered as an `<ng-template>` (`#tplSource`, `#tplLists`, `#tplAlign`, `#tplHistory`, `#tplInsert`, `#tplParagraph`, `#tplFontFamily`, `#tplFontSize`, `#tplTextFormat`, `#tplColor`, `#tplVideo`, `#tplMerge`). A `ResizeObserver` on `.toolbar-scroll` (+ an initial `requestAnimationFrame` pass — RO won't re-fire when clusters render into the fixed-width strip) measures each cluster's cached natural width and — keeping highest-`priority` first — pushes the clusters that don't fit into the `⋮` menu (`recomputeOverflow()`, `visibleGroups()`/`overflowGroups()`, `overflowIds` signal, all measure/collapse debounced through `scheduleRecompute()`). Collapse order (first to go) is by ascending priority: mergeTag → video → color → fontSize → fontFamily → paragraph → align → insert → lists → history → textFormat → source (so the **secondary tools collapse first** and **B/I/U/S + Source survive longest**). The SAME `TemplateRef` renders in either the strip or the menu via `ngTemplateOutlet` (no markup duplication; handlers/signals keep working). Widths are cached per cluster while it's in the strip; all clusters start visible so the first pass measures every one.
- **Two-phase fit + auto-hiding ⋮.** `recomputeOverflow` first checks whether ALL clusters fit without the `⋮` button; if so nothing collapses and the **`⋮` is not rendered at all** (`@if (overflowGroups().length)`). Only when the total overflows does it reserve the (cached) `⋮` width and greedily collapse. So the `⋮` appears exactly when ≥1 cluster is collapsed and disappears when everything fits.
- Display order: Source(`</>`) │ lists (bullet/numbered/checklist) │ alignment dropdown │ undo/redo │ image/link/remove-link/table │ Paragraph / font family / font size selects │ B I U S │ text/highlight **color** │ **video** │ **merge-tag `#`** │ `⋮` overflow (right-pinned via `margin-left:auto`).
- **Source (`</>`) is the ONLY entry to the HTML source view** now that the HTML tab button is hidden (see "view modes" below). Its click → `canvas.toggleSourceMode()`, which just flips `state.mode()` between `'html'` and `'design'` (it no longer uses the legacy `state.sourceMode` signal, which stays `false`); its `[class.active]` reads `state.mode() === 'html'`.
- **All other toolbar buttons are disabled in any non-Design view (Preview OR source).** The `.toolbar-strip` gets `[class.tools-disabled]="state.mode() !== 'design'"`, and the CSS (`kexy-custom-rich-editor.component.css`) dims + `pointer-events:none`s every cluster **except** `[data-group="source"]` (and the `⋮` overflow), so formatting controls can't act on a rendered Preview or the raw-source `<textarea>`. The Source `</>` toggle stays live in both; Design/Preview tabs remain live as an exit.
- The `⋮` **overflow menu** holds ONLY the **collapsed clusters** (rendered via `ngTemplateOutlet`); there is no longer any permanently-overflow content. Color/video/merge-tag are ordinary low-priority clusters that sit in the strip when there's room. In the menu, clusters' in-strip `.tool-divider`s are hidden (`.overflow-menu .tb-group .tool-divider { display:none }`).
- **Font lists must match the approved build** (`fontFamilies`/`fontSizes` arrays on the toolbar component): 21 families (Arial…Comic Sans MS), each `<option>` previewing in its own face via `[style.font-family]`; 22 sizes (8–72px, 14 default). Don't truncate these (they regressed to 5/6 once).
- Opening the merge `#` picker first calls `canvas.captureMergeSelection()` so the caret (body OR subject) is saved before the picker's search input autofocuses and steals it.
- **Active-state sync**: B/I/U/S + bullet/numbered-list + the link button show `[class.active]` reflecting the current selection. `syncFormatState()` (a `document:selectionchange` HostListener, also called right after each `format()` click) reads `document.queryCommandState('bold'|'italic'|'underline'|'strikeThrough'|'insertUnorderedList'|'insertOrderedList')` — but ONLY when the selection is inside the body canvas (`this.canvas.canvas`), so it doesn't flicker when the caret is in the subject/toolbar. The link button (`linkActive`) has no `queryCommandState` equivalent, so it's set by walking up from the selection node to an `<a>` (`closest('a')`). It also calls `syncFontControls()` so the now-inline font family/size selects reflect the selection's font live (they used to sync only on overflow-open). `syncFontControls` reads `canvas.getSelectionFontSize()`/`getSelectionFontFamily()`, which **aggregate across the whole selection** (`resolveSelectionValue` → `selectionTextEls`): they walk every non-blank text node the range intersects and return the shared computed value when ALL agree, else `null` (**mixed**). This is why a **select-all** over an email that uses one font size/family now shows that value in the toolbar — the old code read the selection's `commonAncestorContainer`, which for a multi-block selection is the canvas root and only reported the base 14px/base family. A collapsed caret or text-free selection still falls back to the anchor element. On the mixed (`null`) case `syncFontControls` clears the signal (`fontSize`/`fontFamily` set to `''`) so no single value is implied — each select carries a hidden placeholder option (`<option value="" [selected]="!fontSize()">Size</option>` / `…>Font</option>`) that shows through when the signal is empty, so the control reads **"Size" / "Font"** rather than a wrong value. `syncFontControls` is only ever called from `syncFormatState`, which already bails unless the caret is inside the body, so `null` there always means "mixed", never "caret elsewhere". (Family that resolves to a single but unlisted face is left unchanged rather than blanked.)
- **Alignment active-state**: `syncFormatState` also sets the `alignValue` signal from `canvas.getSelectionAlignment()` (the block(s)' computed `text-align` normalized to `left`/`center`/`right`/`justify`, or `null` when the selection spans differing alignments). The align toolbar button **swaps its icon** to match `alignValue()` (via a template `@switch`, defaulting to the left-align glyph on `null`/left) so it shows the CURRENT alignment, and the align dropdown highlights the matching option with `[class.active]`. `applyAlign` also sets `alignValue` immediately so the button updates without waiting for the next `selectionchange`.
- Dropdowns (overflow, merge-tag, alignment, **table**) anchor with `right: 0` and close on outside-click via a single `document:click` HostListener. They MUST be right-anchored because `.editor-modal` has `overflow: hidden` — a left-anchored menu near the right edge gets clipped.
- **Table = a CKEditor-style hover-to-size grid picker**, NOT a fixed-size insert. The table button (`.table-tool`, in the `insert` cluster) opens a `.table-menu` dropdown with a `.table-grid` of `.table-cell`s. `onTableHover(r,c)` highlights the top-left `r×c` rectangle (`.on` class) and a `{cols} × {rows}` label tracks it; clicking a cell calls `canvas.insertTable(r, c)` and closes the picker. The grid starts `10×10` (`TABLE_GRID_BASE`) and **grows by one row/col when the pointer reaches the last row/col** (capped at `TABLE_GRID_MAX = 20`), so bigger tables need no separate dialog — `gridRows`/`gridCols` signals drive `gridRowRange`/`gridColRange` + the grid's `grid-template-columns`; they reset to base on open. `toggleTable()` calls `canvas.captureMergeSelection()` on open so the caret is saved before the picker steals focus (`insertTable` → `focusEditor()` restores it).

### Subject line (chips, shared toolbar)
- The subject is a **contenteditable** rendered by the host editor component (`.email-meta .subject-input`, above the toolbar), NOT a host `<input>`. It supports the same merge-tag chips as the body — this matches the approved build (the standalone's `subjectInput`).
- Logic lives in `EditorCanvasComponent` (it already owns `MergeTagService` + the fallback popover). The host component registers the element via `editorCanvas.registerSubject(el)` in `ngAfterViewInit`.
- `mergeTagTarget: 'subject' | 'editor'` decides where the toolbar `#` picker inserts. It's derived from **where the caret actually is** — `saveSelection()` sets it to `'editor'` when the range is in the body, `saveSubjectSelection()` sets it to `'subject'` when in the subject (both run on every `selectionchange`).
- `insertMergeTagIntoSubject` restores the saved subject range, then `execCommand('insertHTML', chip+'&nbsp;')` (undoable). Public API on the host component: `@Input() subject`, `(subjectChanged)` output (emits serialized raw on input/blur), `getSubject()` (= `serializeSubjectRaw()`: clone → `stripChipsToRaw` → `textContent`, raw `[tokens]`), `setSubject(raw)` (= `setSubjectContent`: text → `renderChipsInElement`).
- Subject chips hydrate on **load** and on **blur** (NOT live while typing — same caret rule as the body). Clicking a subject chip opens the same fallback popover (`onSubjectClick`); `refreshChipIndicators` re-decorates chips in BOTH the body and the subject.
- Host wiring (`send-email-details-content`): `[subject]="emailSubject" (subjectChanged)="emailSubject = $event"`; `handleSubmit`/`generateEmailContent` read `editor.getSubject()`; the SSE subject push calls `editor.setSubject()`.

### Canvas / editing (`editor-canvas.component.ts`)
- Built on `document.execCommand` (deprecated but works in all current browsers). Bold/italic/lists/color/link go through execCommand and are natively undoable.
- **Alignment (`setAlignment(align)` on the canvas, called by the toolbar's `applyAlign`) uses the native undoable `execCommand('justify*')`, but re-anchors the selection first.** Plain justify broke on merge tags: clicking a chip leaves the selection WRAPPING the chip's `contenteditable="false"` element, and the browser refuses to run a justify command whose selection boundary is a non-editable node — so aligning a line whose content was a merge tag silently no-oped (the reported bug). Fix: before running the command, `setAlignment` re-anchors the selection to span the target leaf block(s)' CONTENTS (`leafBlocksInRange` → `setStart(first,0)` … `setEnd(last, last.childNodes.length)`) so the boundaries sit inside editable blocks; the command then applies `text-align` to the block(s) (the chip moves with the line as inline-level content) AND stays on the browser undo stack (**Ctrl+Z works**). If the selection resolves no block (LOOSE inline content sitting directly in the canvas root — a bare greeting or merge-tag chip with no `<p>`), `setAlignment` first calls `wrapLooseTopLevelInlines()` to wrap it, then aligns the resulting block. Export preserves it (`inlineEmailStyles`' `appendStyle` prepends the block's existing inline `text-align`, never overriding it), so alignment survives preview + the sent email. Media-block alignment is unrelated — that's the inspector's `align-*` classes (`applyAlignment`).
- **Loose root content is wrapped into paragraphs (`wrapLooseTopLevelInlines`).** AI-generated / streamed emails sometimes drop a greeting or a merge tag straight in the canvas ROOT with no `<p>` wrapper (e.g. `Hi Billal,` and a bare `[unsubscribe_link]` as direct children). Such content has no block to carry paragraph styling, so it couldn't be aligned. `wrapLooseTopLevelInlines()` groups each contiguous top-level INLINE run (text/spans/chips/`<br>`/anchors/inline imgs — `<br>`s included so line breaks survive) into ONE `<p>`; block-level siblings + media blocks are separators and untouched; leading/trailing blank text is trimmed so no empty `<p>` is created. It's idempotent and skipped in full-document passthrough (`fullDocTemplate`). Called in `setContent` (BEFORE chip render, so loaded content is normalized on load) and lazily inside `setAlignment` for content that's still loose. NOTE: a pre-existing empty `<p>…&nbsp;<br><br></p>` in generated content is NOT ours — it's a blank line the generator emitted; we deliberately don't strip trailing blank paragraphs (they may be intentional spacing).
- **Color buttons = Google-Docs-style icon + color bar.** In the `#tplColor` cluster, text color renders an **"A" glyph** ("Text color") and fill color renders a **paint-bucket** icon ("Fill color" — the highlight/`hiliteColor` background command), each with a thin **`.color-bar`** underneath (`textColorValue`/`highlightColorValue` signals on the toolbar). The bars are **synced to the text under the caret** (like Google Docs): `syncColorControls()` — called from `syncFormatState()` on every `selectionchange` in the body — reads `canvas.getSelectionColor()` / `getSelectionBackgroundColor()` (computed color of the selection's anchor element, resolved to `#rrggbb`; the fill walks up to the nearest ancestor that actually paints a background). Text color always resolves; fill returns null when there's no explicit background, in which case the bar **keeps the last-used fill** (Google Docs behavior). Picking a color also updates the bar on every `input` tick via `onTextColorInput`/`onHighlightColorInput`. The real `<input type="color">` (`.color-native`) is overlaid transparently (`opacity:0`, absolute inset) so a click opens the OS picker while the visible `.color-face` (icon + bar) shows through. This is purely cosmetic — the live-preview mechanism below is unchanged.
- **Text / highlight color = a live preview wrap, NOT execCommand.** The native `<input type="color">` steals focus the instant it opens, which collapses the contenteditable selection — so `execCommand('foreColor'/'hiliteColor')` can't recolor live and the selection is lost. Instead the color inputs drive three canvas methods: `beginColorPreview(cmd)` on **mousedown** (fires before focus leaves) wraps the live selection in a `<span class="color-preview">` we own; `updateColorPreview(value)` on **input** sets `color`/`background-color` (`!important`) on that span directly — no focus needed, so the text recolors in real time as the picker drags; `endColorPreview()` on **change/blur** drops the `.color-preview` class, unwraps if no color was applied, and re-selects the span. The `.color-preview` CSS background mimics the selection highlight (the native picker hides the real one); for highlight color the live inline `background-color !important` overrides it.
- **Text color on a LINK**: a link's own `<a>` color (UA blue / default) overrides a wrapping color span, so `updateColorPreview` also sets the `!important` color on any `<a>` inside the wrapped span AND on an ancestor `<a>` (`span.closest('a')`). Matching export rule: `inlineEmailStyles` handles `<a>` separately — it only adds the default `color:#2ea3f2` when the anchor has NO color of its own, so a user-applied link color isn't clobbered.
- **Inserting/editing a link uses a popover, NOT `window.prompt`.** The toolbar link button calls `openLinkPopover($event)`, which anchors `LinkPopoverComponent` (`components/link-popover.component.ts` — mirrors the fallback popover's look + focus handling) beneath the button. It pre-fills the URL of the `<a>` under the caret when editing an existing link, otherwise the **last URL entered** (`lastLinkUrl`, remembered across opens). Because the popover input steals focus (hiding the native selection), opening it wraps the selected text in a temporary `.link-target-highlight` span — same trick + look as the color-preview span — so the word stays visibly selected; `clearLinkHighlight` unwraps it (rebuilding `savedRange` over the bare text) on apply, and `onLinkPopoverClosed` (the popover's `(closed)` output) drops it on Cancel/Esc/outside-click. On confirm, `applyLink(url)` normalizes the URL via `EditorUtilsService.normalizeUrl` (so `example.com` → `https://example.com`, matching media-block links), restores the saved body selection, and runs `execCommand('createLink')`; when editing with a collapsed caret it first selects the whole anchor so the href is actually rewritten. The popover dismisses on outside-click via `onDocumentClick` (excludes `.link-popover` and the `.link-tool-btn`). Remove-link stays a separate toolbar button (`unlink()`).
- **Links are NOT underlined by default.** Underline shows ONLY when the user applied it from the toolbar (which produces a `<u>`/`text-decoration` child OR `text-decoration: underline` on the `<a>` itself when the whole link is selected). Email clients underline `<a>` by default, so `inlineEmailStyles` sets `text-decoration:none` on anchors that have no decoration of their own (it skips anchors that already carry one, so a user-applied underline survives). In design view the host's global `a { text-decoration: none !important }` suppresses the *default* underline — but it ALSO clobbered a user-applied one, so the editor CSS re-asserts `text-decoration: underline !important` (higher specificity, beats the global `!important`) for explicit underline markup: `.editor-canvas a[style*="underline"]`, `.editor-canvas a u`/`ins`, and `.editor-canvas a [style*="underline"]`. Without that override, underlining a hyperlinked word did nothing in design view.
- **Font SIZE and FAMILY are NOT execCommand.** `execCommand('fontSize')` only does the legacy 1–7 scale (no arbitrary px) and `execCommand('fontName')` emits a `<font face>` attribute (weakest priority) that the host app's global `font-family: "Lato" !important` reset overrides — so picked fonts never showed. Instead `applyFontSize(px)` / `applyFontFamily(family)` → `applyInlineTextStyle({...})` writes the style with **`!important`** (`style.setProperty(prop, val, 'important')`). An inline `!important` outranks any selector `!important`, so the chosen font/size wins over host globals. Trade-off: these changes are NOT on the native undo stack (correctness over undo, as in the approved build). `applyInlineTextStyle` keys must be kebab-case CSS props (`'font-family'`, `'font-size'`).
  - **Multi-block selections are NOT wrapped in one outer `<span>`** (a select-all size/family change was the bug that motivated this). `applyInlineTextStyle` splits the selection into three kinds and applies each so the value wins in **Design AND the exported/inbox HTML**: (1) **fully-selected leaf blocks** (`<p>/<li>/…`, `TEXT_BLOCK_SELECTOR`, `leafBlocksInRange`) get the prop set **directly on the block** — because export's `inlineEmailStyles` writes `font-size:14px` straight onto each `<p>/<li>`, and a size merely *inherited* from an ancestor span loses to that, whereas the block's own inline `!important` beats the appended non-important default; (2) **partially-selected blocks** wrap just the sliced range in a span; (3) **loose inline text** (a greeting line outside any block) sets the prop on the **outermost fully-in-range wrapper span** (`outermostBlocklessSpan`) so spans don't keep re-nesting/stacking. In all three, `clearPropsOnDescendantSpans` strips the same prop off inner spans so an earlier per-word size can't override the new one. An inline `<span>` wrapping block elements was also fragile — it broke on re-parse (preview iframe/reload), so a select-all size change with an **image (media-block) in the selection did nothing**; styling blocks directly + skipping media blocks fixes that. `normalizeStyledSpans` collapses redundant nested spans afterward.
  - **Merge-tag chips get the prop set on the chip element directly** (a 4th pass: `chipsInRange`, snapshotted before the wraps move nodes). A chip is `contenteditable=false` and holds no text node the three passes above can style; for a **loose** selection the chip can even fall OUTSIDE every wrapper span, so its size/family wouldn't change — and on export the chip becomes bare raw text with no size, reverting to the base in the sent email (**a size change that showed in Design but not Preview**). So: (a) `applyInlineTextStyle` writes the props on the chip inline with `!important` (beats the chip's base CSS, so the pill reflects the size in Design); (b) `MergeTagService.stripChipsToRaw` carries any `font-size`/`font-family` off the chip onto a **wrapper `<span>`** around the emitted `[tag]` text so the size survives export/preview/inbox; (c) `.merge-tag-chip` CSS uses `font-size: inherit` (not a fixed px) so after a reload — when the exported raw tag re-renders as a chip INSIDE that carried span — the pill still shows the right size (an inline per-selection size still wins via `!important`).
- **Host-CSS-override defense:** the host's `src/styles.scss` sets `font-family: "Lato" !important` on a broad reset list, which leaks into the editor. The editor CSS re-asserts its base font on `.editor-canvas` / `.subject-input` and their children with higher-specificity `!important`; per-selection user fonts still win via the inline `!important` above. If fonts ever stop applying again, check for new host `!important` typography rules first.
- **Undo correctness**: anything inserted via direct DOM mutation is NOT on the browser undo stack. So table, images, and videos are inserted via `execCommand('insertHTML', …)` so Undo/Redo works. (Table also appends a `<p><br></p>` spacer.)
- **Merge-tag chips** (`insertChipUndoable`, used for body + subject) must be BOTH inline AND undoable. Plain `execCommand('insertHTML', chip)` promotes the chip to a NEW LINE when the caret is at the END of a paragraph (inserting a `contenteditable=false` element at a block boundary). Fix: `execCommand('insertText', ' ')` first — plain text never promotes, so it lands inline and forces the caret INSIDE a text node — then step the caret back one char (before the space) and `execCommand('insertHTML', chip)` there (now mid-text-node → inserts inline). Both steps are execCommand, so Undo/Redo work (undo removes the chip, then the space). Do NOT replace this with a raw `range.insertNode` — that fixes placement but breaks chip undo.
- **Resize handles use event delegation** (`onResizePointerDown` on the canvas), NOT per-element listeners — so media blocks inserted as HTML (insertHTML / undo-redo / source edit / paste) stay resizable. `createResizeHandle()` only creates the div.
- `insertImageBlock(opts, undoable=false)` / `insertVideoBlock(opts, undoable=false)`: toolbar passes `undoable:true` (uses `insertHTML` + `insertBlock` helper); programmatic sample loading uses `false` (direct append, no undo needed).
- Media blocks are `div.media-block[contenteditable=false]` with `data-*` (kind, width, height, ratio, lockAspect, align, src/poster/link, …). Resizable via the bottom-right `.resize-handle`. Real resizable images/videos need this structure — a bare `<img>` renders but isn't a resizable block.
- **Drag-to-reposition**: media blocks are `draggable="true"` (set on insert + in `hydrateEditorBlocks`) and moved via native HTML5 DnD delegated on the canvas (`dragstart`/`dragover`/`drop`/`dragend`). Placement is **caret-based**: `caretRangeFromPoint` (with a `caretPositionFromPoint` fallback) finds the exact caret under the cursor; `dragover` shows a thin insertion caret (a `position:fixed` div appended to `<body>`, created lazily, removed on destroy); `drop` does `range.insertNode(block)`. This lets a block land between `<br>` lines, between paragraphs, and inside table cells — anywhere a caret can go. The move runs through `execCommand` so it's UNDOABLE (direct DOM moves are not): `insertHTML` the block copy at the drop caret, then select+`delete` the original — so a full undo of a move takes two native steps (delete, then insert). `hoistOutOfParagraph` then moves the inserted copy OUT to a sibling if it landed at the very start/end of a `<p>`/heading (so we don't nest a block in a paragraph), while interior drops (between `<br>`s) stay put. Two guards: dragstart on the `.resize-handle` is suppressed so resizing isn't hijacked; `.dragging` sets `pointer-events:none` (applied on the NEXT tick — mutating the element synchronously in `dragstart` aborts the drag) so `caretRangeFromPoint` reads what's under the block. Export (`transformMediaBlocks`) and `getRawHtml` both query `.media-block` globally, so repositioned/nested blocks still export/round-trip.
- Three view modes share the area: design canvas, preview `<iframe>` (srcdoc), and HTML source `<textarea>`. Source view shows raw `[tags]`; chips re-render on return to design. The tab row (`kexy-custom-rich-editor.component.ts`) renders **Design** and **Preview** buttons; the **HTML tab button is commented out (hidden)** — the HTML source view (`mode === 'html'`) is reached ONLY via the toolbar Source (`</>`) button, and left via Source again or the Design/Preview tabs. (`switchMode('html')` still works programmatically.) In any non-Design view (Preview OR source) all other toolbar clusters are disabled — see the Toolbar section.
- **The HTML tab (`mode === 'html'`) is an EDITABLE source view**, not a read-only export dump. It shows/edits `getRawHtml()` (raw canvas HTML with chips as `[tags]`, full-doc aware — see passthrough below), NOT the inlined `state.htmlOutput()` export; the inlined export is still reachable via Copy/Download HTML. `onHtmlInput`/`onHtmlPaste` route the text through `applyContent` (so a full document switches to passthrough mode), then `hydrateEditorBlocks` → `sanitizeCanvas` → `renderChipsInElement` → `refreshOutputs`; `refreshOutputs` mirrors `getRawHtml()` back into the box, gated by an `htmlEditing` flag so it never clobbers the user's text/caret mid-edit (`htmlEditing` set in `onHtmlInput`, cleared on `onHtmlBlur`/`onHtmlPaste`). The box is **pretty-printed** via `EditorUtilsService.formatHtml` (dependency-free; indents/line-breaks ONLY around block-level elements and serializes inline content verbatim, so it never corrupts inline spacing; idempotent; handles both a body fragment and a full `<!doctype>` document — doctype/`<html>`/`<head>` preserved). Formatting is applied only when mirroring INTO the textarea, NOT when applying edits back to the canvas.
- **Full-document passthrough (`fullDocTemplate`).** If loaded/pasted content is a FULL html document (`applyContent` → `isFullDocument`: has `<!doctype>`/`<html>`/`<body>`), the editor keeps the user's document shell — doctype + `<html>`/`<head>` + `<body>` attrs — in `fullDocTemplate` (with a `<!--KEXY_BODY-->` marker where the body content goes) and loads only the body into the canvas. On export, `generateEmailHtml` re-emits **their** document (`fullDocTemplate` with the current body spliced in via a replacement FUNCTION so `$`-sequences in the body aren't special) and adds **NO** email-table/html shell of ours; `getInlinedBodyHtml` also skips our element style-map in this mode (their doc already carries its own styling — only the border/`--tw` cleanup runs). A fragment clears `fullDocTemplate` (fragment mode → we wrap in the shell as before). `getRawHtml` also re-wraps in the template, so persist→reload (setContent) stays in passthrough.
  - **Table-rooted layout** (`isTableRootedBody`): even without a full-doc shell, if every significant top-level element in the canvas is a `<table>` (trailing empty `<p>`/`<br>`/whitespace ignored), the content is a self-contained table layout that owns its own width/centering. `generateEmailHtml` then wraps it in the document head/`<body>` only — **NOT** our `role="presentation"` 600px email-table shell — and `getInlinedBodyHtml` skips our style map (only border/`--tw` cleanup runs). `isPassthrough()` = `fullDocTemplate || isTableRootedBody()` drives the "skip style map" default.
  - **Plain-text style** (`plainText` flag, set via the `@Input`): emits a head/`<body>`-only document with NO email-table shell, and (like the other passthrough cases — `plainText` IS in `isPassthrough()`) skips our body style map so the sent body matches the raw HTML-tab content. The `<body>` carries the **design canvas's own 14px padding + base type** (`margin:0; padding:14px; background:#fff; font:14px/1.6 Arial; color:#1f2937`) so the Preview and the recipient's inbox have the same edge gap as Design mode. `getHtml()` reflects this (driven by the `plainText` @Input), so preview == `emailContent` == inbox. Table-rooted layouts stay edge-to-edge (`padding:0`); the `generateEmailHtml` branch order is `plainText` (padded) → `isTableRootedBody()` (bare) → default shell. This is reached via the **HTML source tab** and `loadContent`/`setContent` (where the input is the literal source string) — NOT the design-canvas paste, whose clipboard `text/html` is wrapped in `<html><body>` even for a small selection (detecting "full doc" there would wipe the email on an ordinary snippet paste), so design-canvas paste stays a WYSIWYG fragment insert.
- **Layout vs content tables.** Content tables (the table tool inserts `<table>` with no role) get editor sizing/gridlines in design (`kexy-custom-rich-editor.component.css`) + export (`inlineEmailStyles`). Layout tables — `role="presentation"` (pasted email shells, our media-block wrappers) — keep their own sizing/spacing and get NONE of our `width:100%`/border/padding, in both design CSS (`table:not([role="presentation"])`) and export (skip `table[role="presentation" i]` and any `td`/`th` inside one).
- **Phantom-border cleanup on input/paste.** Content pasted from Tailwind-styled sources (or Word/Google Docs) carries `border-style: solid` with no width/color — invisible in the design canvas (host reset zeroes border-width) but a dark `medium` border in a bare email document/inbox. `EditorUtilsService.neutralizePhantomBorders(root)` zeros the width of any border side with a visible style but NEITHER explicit width NOR color (deliberate borders — explicit width/color, `<hr>`, blockquote, table cells — are left alone). It runs: on **design-canvas paste** (next tick, after native paste settles — see `onPaste`), on **Source/HTML-tab input**, and inside **export** (`inlineEmailStyles`). Cleaning lives ENTIRELY in the editor — consumers (drip save/preview) persist and render `getHtml()` output as-is.
- **Tailwind cruft removal.** Content pasted from Tailwind-styled pages carries `--tw-*` inline CSS custom properties (translate/rotate/scale/blur/gradient reset vars). We don't use Tailwind, so `EditorUtilsService.stripTailwindVars(root)` removes every `--tw-*` inline property (and drops the `style` attr if that empties it). Tailwind utility *classes* are intentionally left alone (inert in email; blanket class removal would strip our own `merge-tag-chip`/`media-block`). It runs at the SAME points as the border cleanup: the canvas's `sanitizeCanvas()` helper (paste + Source/HTML-tab input) bundles `neutralizePhantomBorders` + `stripTailwindVars`, and `inlineEmailStyles` calls both on export.
- Export (`generateEmailHtml`) clones the canvas, strips chips to raw tags, removes resize handles / contenteditable, normalizes font tags, inlines styles, and wraps in a table-based email shell.
- **Image upload**: the toolbar's `onImageFile` computes dimensions from the local file, then calls the optional `toolbar.uploadImage(file)` callback to get a hosted URL for the block `src` (so exported emails reference a hosted image, not base64). The host component (`KexyCustomRichEditorComponent`) wires this in `ngAfterViewInit` to its `sendFile()` → `{ default: url }` against `apiUrl` (`landing-pages/save-image`). If no uploader is wired, or upload fails, it falls back to an inline base64 data URL. NOTE: this makes the editor no longer fully self-contained — `sendFile`/`apiUrl` depend on `environment` + an auth token in localStorage.
- **Video poster from a real frame**: `onVideoFile` calls `EditorUtilsService.captureVideoPoster(file)` — loads the file into an off-DOM `<video>` (object URL → same-origin, untainted canvas), seeks ~0.2s in, draws the frame to a canvas, **bakes the play-button badge into the frame (`drawPlayBadge`)**, returns a JPEG data URL + real dimensions (block width stays 420, height from the true ratio). The poster is uploaded via the same `uploadImage` callback (hosted URL in exports), falling back to the inline frame, and finally to the generic `buildVideoPlaceholderSvg` play-button thumbnail if decoding fails. The captured poster flows through the existing `data-poster` path; `onVideoFile` inserts with `overlayBaked:true`.
- **Custom video thumbnail**: when a video block is selected, the media inspector shows an "Upload custom thumbnail…" button (video-only) → `EditorCanvasComponent.replaceSelectedVideoPoster(file)`. It reads the file to a data URL, **composites the play-button badge into it (`EditorUtilsService.compositePlayButton`, untainted because the source is a local file)**, uploads the BAKED image via the shared `uploadImage` uploader (now wired by the host onto BOTH the toolbar and the canvas), falling back to the inline baked data URL, then updates the visible `.video-thumb img` src + `data-poster` and sets `data-overlay-baked="1"` / `.has-baked-overlay` so design/preview/export all use the new thumbnail with its play button.
- **Media-block link normalization**: a click-through URL typed without a scheme (`www.x.com`, `x.com/watch`) is otherwise treated as RELATIVE to the portal domain, so the image/video link points at the wrong URL. `transformMediaBlocks` runs both the image link and the video `href` through `EditorUtilsService.normalizeUrl`, which prepends `https://` when no scheme is present (leaving `#`/`/`/`//`/`[merge-tag]`/already-schemed values untouched).
- **Existing videos get the badge on load too**: `setContent` calls `bakeOverlayOnLoadedVideos()` — for any `.video-block` lacking `data-overlay-baked`, it composites the play badge onto the current poster and (if an uploader is wired) re-hosts it, so videos saved BEFORE baking also show the play icon in preview/email. Best-effort: cross-origin posters without CORS taint the canvas and are left unchanged; SVG placeholder posters are skipped (they already draw their own button). New inserts/thumbnails remain the guaranteed path (they bake + upload a fresh poster).
- **Play overlay — baked into the poster image, NOT an export-time HTML overlay.** Email clients can't reliably composite a CSS/HTML overlay (no absolute positioning; spotty `<td background>` support), so the play-button circle+triangle is drawn straight INTO the poster bitmap at creation time: `drawPlayBadge` for captured frames, `compositePlayButton` for custom thumbnails, and `buildVideoPlaceholderSvg` draws its own. The badge is a translucent white disc + a solid white right-pointing triangle (its centroid sits at the disc center so it reads optically centered) + a soft drop shadow, sized as a % of the image so it scales consistently. `drawPlayBadge`, the placeholder SVG, and the design-view CSS overlay all share this look — keep them in sync if you restyle it. Because the image carries the button, it survives **design → preview → export → the recipient's inbox** unchanged. Blocks with a baked poster get `data-overlay-baked="1"` (persisted in the saved HTML, restored in `hydrateEditorBlocks`) + the `.has-baked-overlay` class. The legacy CSS `.video-block:not(.has-baked-overlay) .video-thumb::after` overlay now renders ONLY for old saved videos whose posters predate baking, so they keep a design-view play button without doubling up on baked ones.

### Layout / styling
- All editor styles live in `kexy-custom-rich-editor.component.css`, applied globally via `ViewEncapsulation.None` (REQUIRED — chips, media blocks and resize handles are created imperatively and never pass through an Angular template, so scoped styles wouldn't reach them).
- **Content-height layout** (NOT flex-fill) by default: host → `.page-shell` → `.editor-modal` are plain flex columns with no forced height/`flex:1`/internal `overflow`. `.editor-modal > section` is the bordered card (children = `.email-meta` subject row [above the toolbar, flex:0 0 auto], toolbar, `.tab-row`, `app-editor-canvas`); it grows with the canvas. `.editor-canvas` has `min-height: 320px; overflow: visible` so it grows with content instead of scrolling. The `app-media-inspector` ("Selected media") is the last child of `.editor-modal` (`flex:0 0 auto`) and simply stacks below — since nothing is height-bounded, it never squeezes the editor and the outer container scrolls to reveal it.
- **Fill-height mode** (`.fill-height` host class, set by `[fillHeight]`): the same chain switches to flex-fill — `kexy-custom-rich-editor.fill-height` gets `flex: 1 1 auto` with a **`min-height: 420px` floor** (see below), and `.page-shell`/`.editor-modal`/`.editor-modal > section`/`app-editor-canvas`/`.mode-panel.active` all get `flex: 1 1 auto; min-height: 0`, while `.editor-canvas` additionally gets `overflow-y: auto` so it scrolls INTERNALLY (Source/HTML textareas + preview iframe drop their fixed `60vh` for `flex:1` too). `.email-meta` and `app-media-inspector` stay `flex:0 0 auto`, and the toolbar sits above the scroll, so subject + toolbar + inspector stay pinned while only the canvas scrolls. Requires the host to bound the height (see `send-email-details-content`: `.canvas-body` is the flex column + scroll container, and `.form-section.editor-section` + `.ckeditor-wrap` + the editor are `flex:1 1 auto; min-height:0`). **Every wrapper in that chain must keep `min-height: 0`** — that is what bounds the host. Drop it anywhere and the wrapper takes a content-based minimum, so the editor grows with its content instead of scrolling internally, and the pinned toolbar/subject scroll off the top out of reach. If the consumer needs a short-viewport floor, put it on a wrapper ABOVE `.ckeditor-wrap` (send-email puts it on the section card) rather than on the host, so the editor stays bounded by — and visually inside — that wrapper.
  - **Small-screen floor:** the editor host's `min-height: 420px` (NOT `0`) means on a short viewport the editor keeps a usable minimum height instead of collapsing to the available sliver — the host's own scroll container (`send-email`'s `.canvas-body`, `overflow-y:auto`) then scrolls to reveal it. On a tall viewport `flex-grow` still fills the space (the min-height only floors it) so the canvas keeps scrolling internally. The DESCENDANT fill rules keep `min-height: 0` (that's what lets the inner canvas scroll) — only the HOST carries the floor. **NOTE:** this 420px is only the editor's package DEFAULT; a consuming page can (and `send-email-details-content` does) override it with a MORE SPECIFIC rule — `send-email-details-content.component.scss` overrides it to `min-height: 0` and puts its floor on the SECTION CARD above the editor instead (`.form-section.editor-section { min-height: 460px }`) — that keeps the editor bounded (toolbar stays pinned) AND guarantees the editor can't outgrow the bordered card it sits in. So the send-email drawer's actual floor is tuned THERE, not here. If a consumer ever does set a real floor on the host, scope it `:not(.fullscreen)`: a consumer rule that specific also out-specifies the `.fullscreen` reset below, so an un-guarded floor taller than the viewport beats `height: 100vh` and hangs the fullscreen editor off the bottom of the screen.
- **Full-screen mode** (`.fullscreen` host class): a toolbar toggle expands the editor to cover the whole viewport and back. State is the `EditorStateService.fullscreen` signal (`setFullscreen`/`toggleFullscreen`); the host reflects it via `@HostBinding('class.fullscreen')` (a getter reading the signal). Enter/exit from the **`fullscreen` toolbar cluster** (`#tplFullscreen`, expand/compress icons swapped on `state.fullscreen()`) — it has `priority: 100` so it's the LAST to collapse into the `⋮` menu, and it's exempted (alongside `source`) from the `.tools-disabled` dim so it stays clickable in Preview/HTML modes too. There's ALSO a **floating `.fullscreen-exit` (X) button** in the top-right corner, rendered ONLY while `state.fullscreen()` (`@if` in the host template), that calls `setFullscreen(false)` — a round white button absolutely positioned in the host's corner; the subject input gets `padding-right: 48px` in fullscreen so its text stays clear of it. **Esc also exits**, but via a **capture-phase** `document` `keydown` listener (`onEscapeCapture`, added in `ngAfterViewInit` with `{capture:true}` outside the Angular zone, removed in `ngOnDestroy`) — NOT a bubbling `@HostListener`. The editor lives inside an ng-bootstrap `NgbOffcanvas` (opened via `generate-drip-campaign`'s `__createRightSideSlide`, `keyboard:true` by default) whose own Escape handler is registered on `document` FIRST (when the drawer opened), so a bubbling listener would fire too late and the drawer would already have closed. Capturing lets us run first: while `state.fullscreen()` we `preventDefault` + `stopPropagation` + `stopImmediatePropagation` so the offcanvas never sees the key (drawer stays open) and only exit fullscreen (re-entering the zone via `NgZone.run` for CD). When NOT fullscreen we do nothing and let Esc bubble on so it still closes the drawer as before. The CSS pins the host `position: fixed; inset: 0; z-index: 100000; background: #f4f6fb; padding: 16px` and force-applies the SAME flex-fill rules as fill-height (regardless of the `[fillHeight]` input, and its `min-height:0` here overrides the fill-height 420px floor since `height:100vh` wins) so the toolbar/subject/inspector stay pinned and only the active view scrolls — **nothing about the editor's structure or behavior changes**, it just fills the screen. `ngOnDestroy` resets the signal to `false` because `EditorStateService` is a root singleton (a lingering `true` would reopen the next editor instance fullscreen).
- The bordered "card" is the inner `<section>` (border/background/radius/overflow + `:focus-within` highlight live there), NOT `.editor-modal` (which is just a layout column). This is deliberate: the `.email-meta` subject line sits ABOVE `<section>` and OUTSIDE its border, so it reads as a separate field. There is NO `.editor-card` element in the template even though the class exists in CSS.
- Border radii: boxes/controls/menus = **5px**; pill shapes (chips, status pill) = `999px`; true circles (the `#` badge in the picker, resize handle, fallback ↩ marker) = `50%`.

## Gotchas / caveats

- **`EditorStateService` is `providedIn: 'root'` (a singleton).** Two `<kexy-custom-rich-editor>` instances on one page would SHARE state (mode, selected block, output). For multiple independent editors, move `EditorStateService` (and likely the others) into the component's `providers: []`.
- `execCommand` is officially deprecated. Works everywhere today; a future rewrite would replace it with a Selection/Range-based command layer.
- Checklist (`insertChecklist`) renders checkbox markers via CSS `::before`; email HTML strips pseudo-elements, so exported checklists are plain `<ul>` lists.
- Beware invisible characters: the codebase previously had a stray non-breaking space (U+00A0) inside a string literal that broke exact-string edits. If a string edit mysteriously won't match, check for non-ASCII whitespace.
- After Undo removes a selected media block, `EditorStateService.selectedBlock` can briefly point at the detached node until you click elsewhere (which clears it).
